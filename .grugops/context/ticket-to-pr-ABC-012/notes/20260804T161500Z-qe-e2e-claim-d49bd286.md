# What this gate could NOT settle, named for the roles that own it

Every item here is a `claim` at `confidence: UNKNOWN - verify`. **No `finding` is written on this
install — there is no §14 gate to issue a stamp, and no role may self-stamp.** None of these is
load-bearing for the PASS; each is a lead with its reason for being a lead and its owner.

## 1. `takeBack(history, NaN)` silently discards the entire game — owner BA/PM, consumer `ABC-019`

Measured, not suspected, on the shipped module:

| call from a 10-ply game | result |
|---|---|
| `takeBack(h, NaN)` | **`moves.length === 0`, position back at the anchor, no throw** |
| `takeBack(h, undefined)` | **same — the whole game gone** |
| `takeBack(h, 1.5)` | takes back **2**, not 1 |
| `takeBack(h, -1)` | no-op — correct, exactly as Decision 3 says |
| `takeBack(h, Infinity)` | clamps to 0 — correct |
| `takeBack(h, -Infinity)` | no-op — correct |

`Math.max(0, NaN)` is `NaN` and `splice(NaN)` starts at index 0, so the clamp that exists to prevent
silent corruption passes this input straight through into total silent data loss.

**Why this is not the impossible scenario `AGENTS.md` rule 8 excludes, and why it is a different
case from the negative `plies` the Engineer deliberately left alone.** A negative `plies` is a benign
no-op; `NaN` destroys the game. `NaN` is a `number` to TypeScript, so the type system does not
exclude it. `EPIC-006` / `ABC-019` own the turn loop and will parse a ply count from user input —
`Number.parseInt("abc")` is `NaN` — so `undo abc` reaching this function is an ordinary path, not an
exotic one. The ticket's own justification for the clamp is *"a silent-corruption path, not an
impossible one"*, and that sentence describes this input better than it describes the one it was
written for.

**Not fixed — QE does not change production code. Deliberately NOT pinned by a test either**: a test
asserting today's output would enshrine the behaviour and make the eventual fix look like a
regression. Whether to guard it, and where — here or at the `ABC-019` call site — is BA/PM's to rule.

## 2. `src/history.ts:42` claims the borrow contract is tested. It is not — and two documents disagree about it

The doc comment on `GameHistory.position` reads *"Read it; never mutate it, and do not hold the
reference across a `takeBack`. The contract is documented and tested, not typed"*.

Two problems, both verified:

- **It is not tested.** No test in `src/history.test.ts` touches `history.position.board`, and the
  Engineer's own claim note says so in its item 5. The sentence in the shipped file says otherwise.
- **It contradicts the decision note and this ticket's implementation record**, which say a caller
  holding `h.position` across a take-back **keeps a valid reference**, because `takeBack` rebuilds
  the object in place. That is true of the shipped code. So the code comment forbids what the notes
  call safe.

The doc comment errs in the **safe** direction, which is why this is not a defect and not a blocker.
But `ABC-019` is the first caller and will read one of the two; they should not disagree. **Named,
not fixed** (it is production-code text). This gate deliberately did **not** add a test pinning
identity-preservation across `takeBack`: the shipped comment tells callers not to rely on it, and
pinning behaviour the module documents as unreliable would freeze the wrong side of the ambiguity.

## 5. `playMove` validates nothing, and this gate did not re-open that

fails if a caller passes a move from a different position; the documented precondition is the whole
defence. Unchanged, unre-opened, and repeated only so it does not drop out of the trail now that the
module exists and `ABC-019` is unblocked.

## 6. The double-push repetition test — declined here, and the reason is a routing claim

The Orchestrator named it for this column and deliberately did not order it. **This gate declines
it**, and the reason is a claim rather than a proof: such a test would pass or fail entirely on
`src/zobrist.ts`'s behaviour (`ABC-011`'s, merged and gated twice), because `src/history.ts` only
consumes `zobristKey` and cannot distinguish two hashes. A test asserting another module's property
from this module's file is filed in the wrong place. If a later role disagrees, the fact worth
carrying is the one the Engineer recorded: since `ABC-011`, `src/zobrist.ts:85` hashes the ep file
only when a **legal** ep capture exists, so a repeated line containing a double push with no capture
available now hashes **equal** — such a test would today assert something it could not have asserted
before `ABC-011`. Owner: `ABC-011`'s trace row.
