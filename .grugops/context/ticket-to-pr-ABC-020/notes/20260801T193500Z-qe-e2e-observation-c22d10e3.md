# Thirteen mutations run against the delivered suite — four survived, all four were ORDER or SHAPE

A green suite proves nothing unless it goes red when the code is wrong. I mutated `src/gameend.ts`
in a throwaway `git worktree` at `HEAD` (the branch itself was never edited) and ran
`src/gameend.test.ts` against each. **This is the check the `ABC-007` gate did not make**, and it is
the only reason the four holes below were found.

## The nine mutants the delivered suite killed

| Mutation | Tests failed |
|---|---|
| `by: "white"` unconditionally — **the exact G-1 defect** | 2 |
| `by` inverted (claim to the side that just moved) | 8 |
| threefold `>= 3` → `> 3` | 4 |
| fivefold `>= 5` → `> 5` | 2 |
| 75-move `>= 150` → `> 150` | 3 |
| fifty-move claim `>= 100` → `> 100` | 4 |
| fifty-move draws automatically again (**the reverted defect**) | 6 |
| threefold draws automatically again | 4 |
| `draws` order reversed (fifty-move first) | 1 |
| `claimable` always present, empty array when nothing is claimable | **12** |

The last row is the one worth reading twice: it is the design hop's shape argument, measured. Making
`claimable` present-and-empty fails **12** tests, of which **8 are among the 18 whole-object
`toEqual` assertions `A9` forbids touching**. So those 18 are not inert — they now also assert that
nothing is claimable in their positions, exactly the free bonus the design note predicted, and they
would have caught a `null` / `[]` / new-tag-field shape. `A9` is a real constraint and it held.

## The four that SURVIVED — every one an ordering, and each one changes a reason, never a result

| Surviving mutant | Effect | Why nothing noticed |
|---|---|---|
| `isInsufficientMaterial` moved **below** the 150-ply clock check | K vs K at clock ≥ 150 reports `seventy-five-move` | both are `draw`; only the reason moves |
| `isInsufficientMaterial` moved **below** the fivefold check | K vs K at five occurrences reports `fivefold-repetition` | same |
| the zero-legal-moves branch moved **below** `isInsufficientMaterial` | a stalemate in a material-thin position reports `insufficient-material` | same |
| the 150-ply check moved **below** the fivefold check | five occurrences **and** clock ≥ 150 reports `fivefold-repetition` | same |

**The ticket claims this is guarded and it is not.** `## Out of scope` says the zero-legal-moves
branch running first "is load-bearing. Acceptance **A6** pins it." A6 pins **checkmate against the
clock** — a different pair. The pair the ordering actually protects (zero-legal-moves against the
material test) had no assertion at all, and neither did the material test against either automatic
draw rule. R-4 named the ordering load-bearing; nothing in the suite bore the load.

**Product severity is LOW** — a wrong reason string, consumed only by `EPIC-006`'s result screen,
never a wrong result. `isInsufficientMaterial` is correct (R-1, 18/18), so a checkmate position can
never be material-thin and the mutants cannot turn a win into a draw. **Gate severity is higher:**
a document asserting a guard that does not exist is how `ABC-007` passed.

## What I added — six tests, all green, skip count still 0

In `src/gameend.test.ts`, two new `describe` blocks. I changed **no production code**.

1. **`gives the claim to Black when it is WHITE's move that makes the third occurrence`** — the
   played-line mirror of A1. A7 flips the side to move on a synthetic counts map, which cannot
   express who *created* the occurrence; the ticket's own *Test notes* item 3 says a one-FEN test
   cannot express the asymmetry, and only one colour had a played line. Now both do.
2. **`decides no-legal-moves and thin material BEFORE the clock and the counts map`** — kills the
   first three surviving mutants in one assertion pair (`7k/5K2/5N2/8/8/8/8/8 b - - 150 90` and
   `4k3/8/8/8/8/8/8/4K3 w - - 150 90`, both with a five-occurrence counts map). The `stalemate`
   label here is **G-4's known divergence** — FIDE would call 5.2.2 the operative article — and the
   test says so in a comment: it pins the ORDER the ticket chose, not the label's correctness.
3. **`terminates the locked wall on a second no-progress line`** — A5 drives the *first* quiet move
   each ply; this drives the *last legal* move, an independent line. Both reach exactly ply 150 with
   `seventy-five-move`, so the termination is a property of the position, not of A5's move filter.
4. **`still terminates the locked wall on a line that DOES capture — 150 plies per epoch`** — see
   the A5 note; this is the epoch claim pinned as a test rather than left in prose.
5. **`cannot spell a claimable draw as a completed draw, or a claim without a claimant`** — six
   `@ts-expect-error` negatives, so the ratified shape's **rule 3** is enforced by
   `npm run typecheck` instead of by an out-of-tree harness.
6. **`lets a consumer read the claim off the bare union with no narrowing`** — `ABC-016`'s panel
   cell and `ABC-021`'s prompt both depend on `status.claimable?.draws ?? []` typechecking without a
   narrow, so it is pinned here rather than discovered there.

**Re-run after the additions: all four surviving ordering mutants now fail** (each on the new
order test), and the 75-move off-by-one now fails five tests instead of three.

## The type guards were verified to bite, not merely to compile

`@ts-expect-error` is worthless if the line stops being an error, so I mutated the **types** and
confirmed `tsc` reports `TS2578 Unused '@ts-expect-error' directive`:

| Type mutation | tsc result |
|---|---|
| `EndReason` widened back to include `threefold-repetition` + `fifty-move` | 2 directives reported unused |
| `DrawClaims.by` made optional | 1 directive reported unused |
| `GameStatus` collapsed back to a single arm | 2 directives reported unused |

I also re-verified the Engineer's seven forbidden states independently, out of tree, under this
repo's exact flags (`strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`,
`verbatimModuleSyntax`), plus three of my own. **All ten are genuine compile errors.** The Engineer's
claim was accurate; what was missing was only the permanent guard, and it now exists.

## One ordering left deliberately unpinned, and it is flagged rather than fixed

Five occurrences **and** clock ≥ 150 reports `seventy-five-move`, never `fivefold-repetition`. Both
are automatic, the result is identical, and FIDE would say whichever condition arose first is
operative — which a pure function of a position cannot know. **Pinning it would lock an arbitrary
choice**, so I did not. Recorded for `EPIC-006`'s result screen.

**A second reason not to pin it, and this one is Security/NFR's, not mine:** the 150-ply check
sitting *above* the key read is what makes the Engineer's A10 bar-2 measurement (`zobristKey` = 0
when the clock decides) true. Moving it below the fivefold check would break that bar and **no test
would notice.** I did not measure the NFR bars — that review is next and two roles measuring the
same thing is waste — but the missing guard is named here so it is not discovered later.
