## The three flagged items, each ruled on the evidence

**Item 1 — `(+N more)` has no defined width. AGREED, and it is worse than the flag said.** The width
half is confirmed independently (see the observation note: zero `columns|width` hits in non-test
`src/` on merged `main`, and **no width at all in append mode**). Carrying it one step further
changes the severity: with any plausible width the criterion's own example is **self-defeating** —
six 4-character SANs need 29 characters, a 2-row region at `W = 18` holds 36, so a correct
implementation shows **all six**, emits **no** marker, and **fails the criterion as literally
written**; a one-candidate-per-row implementation answers `N = 5` and passes. Two correct
implementations disagree and one reading makes the criterion vacuous. This is `ABC-015`'s defect 1
exactly: an input tuple with no stated output.
**RULED:** the frame has **one width `W`, a session constant** = the widest row the assembled regions
emit; `process.stdout.columns` is **not** read (it does not exist in append mode and the frame is a
session constant by the epic's SIGWINCH ruling). The region takes a **list of items**, each placed
whole or not at all. **`N` is defined relationally** — the count of supplied items the region does not
show in full — so **packing stays the engineer's** and only `N` is pinned. One criterion became two:
a *fits* case and a *does-not-fit* case, each carrying its arithmetic. A smaller wrinkle falls out of
the same ruling: a newline is a C0 character the sanitizer removes, so the *"2-line rejection"* in
criterion 2 was never one string with a `\n` in it.

**Item 2 — the frame's row count is never specified. AGREED IN SUBSTANCE, DIAGNOSIS CORRECTED, and
the corrected fault is the most serious of the five.** `23` is **not** unsourced: it is `EPIC-002`
`4a`'s reference layout, `9 + 3 + 8 + 2 + 1 prompt = 23`. The real fault is one row down — **this
ticket's `## Scope` assembled four of those five regions and sums to 22**, while its criteria are
written against 23. Grepped across every ticket in the epic and `EPIC-003`: **no ticket owned the
prompt row**, and `ABC-016` records that `ABC-018` owns *"all writing"*. The row the player types
into was inside the epic's frame, outside this ticket's frame, and owned by nobody.
**Why that is not bookkeeping:** *"the TTY reports at least as many rows as the frame"* would have
been short by exactly one row, and the first keystroke scrolls the frame origin off the top — which
is the precise failure `4b` exists to prevent, arriving through the one row nobody counted.
**RULED:** the frame **reserves** a 1-row prompt row as its last row, inside `H`; the in-place write
leaves the cursor at its start with **no trailing newline**; `EPIC-003` keeps the prompt surface and
this ticket renders nothing into the row. `H` is stated as a session constant known before the first
frame, which is what makes a once-at-startup strategy choice well defined, and the `23`s in the
criteria are labelled as the epic's reference layout used as a **stub fixture**, never a hardcode.
**The alternative is recorded rather than picked silently:** leave the frame at 22 and require
`R ≥ H + 1`. Rejected — it fixes this ticket's omission by **amending the epic's own rule**
(`4b`/`4c` say *"as many rows as the frame"*) and pushes the accounting into `ABC-019`, which does
not write.

**Item 3 — the in-place strategy's boundary is untested at equality. AGREED.** Added a **23/23**
criterion asserted on the screen model. It kills **two** named mutants rather than the one the flag
named: `>` where the rule says `≥`, **and** a trailing newline after the frame's last row — at
exactly this size that newline scrolls the origin off the top and every later redraw lands one row
high. The two rulings meet here: the boundary case is only correct *because* the last row is the
reserved prompt row written without a newline.

## The two the pre-check did not name

**4 — `NFR-002`'s bar was ambiguous by 2x.** *"When compute and write are measured separately …
then **each total** is < 16 ms"* reads as *each half* < 16 ms and passes a 31 ms frame against a
16 ms bar. It contradicted its own ticket (`## Security / NFR triggers`: *"compute + write < 16 ms"*)
and `plans/traceability.md`'s `ABC-018` row. **Rewritten to the SUM at each ply count, both halves
still recorded separately with their machine. NO TARGET MOVED** — the 16 ms is `EPIC-002`'s.

**5 — a criterion that could not fail: the `ABC-015` defect-2 shape, again.** *"When
`process.stdout.isTTY` changes afterwards, then the strategy in use is unchanged"* names an **ambient
global the design this ticket's own `## Test notes` mandate never reads** — the writer is exercised
against a captured sink — so it passes for **every** implementation, including one that re-decides on
every write. **Restated against the injected sink** (mutate its `isTTY` and rows after construction,
write two more frames, both must still be in place). Unlike `ABC-015`, the mutant here is **live**:
the signals sit on a stateful object the writer holds, so re-reading them per write is a plausible
implementation, not a forbidden one.

**A sixth collision, folded into the Security bar rather than counted as a defect.** Acceptance `2a`
asserts **zero** code points above `U+007F` over the **whole** emitted stream in ASCII mode, while the
sanitizer removed only C0 and `U+007F`. `EPIC-003` will echo what the player typed, so `é` made two
of this ticket's own criteria contradict each other. **RULED:** in **ASCII mode only**, supplied
strings also lose code points above `U+007F`; in Unicode mode they survive, because a UTF-8 terminal
can draw them and ASCII mode exists for the one that cannot.

## What was adjudicated and deliberately left alone

- **Acceptance criterion 1** (*identical row count at 80 and 300 plies*) is **near-vacuous under the
  stub panels this ticket is built against** — a constant-height stub makes any assembler pass. Left
  exactly as it is: it is epic `4a` verbatim, it becomes falsifiable at integration (`ABC-019`,
  `EPIC-006`), and under stubs the falsifiable weight is carried by the criterion beneath it, which
  varies message content and thinking state in one run. Recorded so the silence is not read as an
  oversight.
- **No median/p95 statistic** was added to the `NFR-002` criterion. This repo has no in-repo
  wall-clock bars by convention (`src/zobrist.nfr.test.ts:112` says why) and the figures are
  re-derived out-of-tree at the Security/NFR gate.
- **`EPIC-002` was not edited.** The corrections make the ticket match the epic's own reference
  layout; nothing in the epic had to change. **`ABC-016`, `ABC-017` and `ABC-019` were not edited and
  are not vouched for** — this subtask promoted one ticket.
