# An empty locale variable counts as UNSET — the Engineer's ruling is RATIFIED, and it is now SPECIFIED rather than inferred

This is the one of the three items that **could** have changed code. **It does not.** The Software
Engineer implemented the POSIX reading, flagged it at `confidence: medium` as an inference from an
adjacent rationale, and asked for it to be read rather than inherited; QE concurred and left it open
because it can change code. **Read, and ratified.** What follows is the evidence it rests on, because
"two roles already thought so" is not evidence.

## The ruling

**A locale variable set to the empty string counts as UNSET, and precedence falls through to the next
variable.** `LC_ALL=` with `LANG=en_US.UTF-8` is **unicode**, not ascii.

## Three pieces of evidence, in the order they carried weight

1. **This ticket's own rationale for row 4 requires it, and that rationale is not mine or the
   Engineer's — it predates both passes.** It reads: *"Unset is the normal Windows case and carries
   no information; treating it as a negative signal would smuggle the platform rule back in through
   the side door."* An empty `LC_ALL=` carries no information either. The literal reading turns a
   content-free variable into a negative signal, which is the move that sentence exists to forbid.
2. **POSIX, checked on this machine rather than recalled.** A locale variable is consulted only when
   it is "defined and not null". Verified: `env -i LC_ALL= LANG=en_US.UTF-8 locale` reports
   `LC_CTYPE="en_US.UTF-8"` — the empty `LC_ALL` fell through — while `env -i LC_ALL=C
   LANG=en_US.UTF-8 locale` reports `LC_CTYPE="C"`. **The rule this ticket already describes in words
   is the one the platform underneath it implements**, so the POSIX reading also costs a reader no
   surprise.
3. **The product value statement breaks the tie, and it is the reason this is a BA/PM call at all.**
   The ticket's value is *"the majority get figurines with no flag and no prompt; the minority get a
   readable board and one documented flag to reach it."* `LC_ALL=` is exported by CI images and shell
   wrappers in the wild. Under the literal reading, that one empty variable **freezes the precedence
   at the first rung** — a perfectly good UTF-8 `LANG` is never consulted — and hands ASCII to
   exactly the player row 5 exists to serve. The tail that genuinely needs ASCII already has
   `--ascii`, documented in `--help`.

## Why this does NOT contradict the both-flags-true ruling, which chose the fail-safe direction

Stated because the tension is real and a reader will find it. On 2026-08-08 this role ruled
`(--ascii, --unicode)` both true to **ascii** on fail-safe grounds — a wrong ASCII board is legible,
a wrong Unicode board is `????????`. The same instinct would give `LANG=""` → ascii. It does not
apply, and the difference is in the input, not in the appetite for risk:

- **Both flags true is a CONTRADICTION** between two explicit user requests. There is a genuine tie
  between two stated intentions, and the fail-safe direction is a defensible way to break it.
- **An empty variable is the ABSENCE of information.** It is not a user saying "my terminal is not
  UTF-8"; it is a user saying nothing. Reading absence as a negative signal is what row 4's rationale
  forbids by name, and it is also what the default-is-Unicode rule already settles for the unset
  case.

Different inputs, different rule. **Both rulings stand together, and neither was re-opened.**

## What changed in the ticket, and what deliberately did not

**Changed:** a fourth bullet under `## Scope` defining "set" as *set to a non-empty value*, and one
new acceptance tuple (criterion 14) pinning `LC_ALL=` with `LANG=en_US.UTF-8` → `unicode`.

**The point of the change is that the behaviour stops being an unmarked judgement call living in a
code comment.** It was correct and it was flagged honestly, but a rule that only exists in
`src/glyph-mode.ts`'s comment is one refactor away from being "tidied" — and the criteria could not
catch it: measured, the literal reading satisfies **all nine** original tuples.

**Not changed: the code.** `src/glyph-mode.ts` already implements exactly this
(`if (value === undefined || value === "") continue;`), and the Engineer's existing test — *"falls
through an empty variable to the next one in precedence order"* — asserts the exact tuple criterion
14 now states. **Nothing is owed to the Software Engineer and no QE re-run is owed.** If the ruling
had gone the other way it would have been one condition in `selectGlyphMode`, two test rows and a QE
re-run, and this note would say so plainly.

## What this decision does NOT do

- **It does not touch `EPIC-006`'s argv obligations.** How an empty variable arrives is not this
  ticket's business; what the rule does with one is.
- **It does not ratify anything else the Engineer or QE flagged.** The `Boolean()` comment is the
  Engineer's sentence in a production file and is untouched here; the absent-`isTTY` shape needed no
  criterion, because table row 3 already says *falsy* and `undefined` is falsy.
- **It does not move the ticket.** `ABC-015` stays in `In Security/NFR` and that exit is

- **It does not pre-empt the Security/NFR gate's own re-derivation** of this ticket's "no security
  trigger" claim. This function reads `process.env`; that re-derivation is the gate's and is still
  ahead.
