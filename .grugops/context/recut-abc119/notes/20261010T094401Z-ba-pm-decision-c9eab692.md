### P2 / proposal 2 — `N8_SPAWN`: TAKEN, second branch. The lane is ruled OUT of `src/cli.test.ts`.

The Engineer offered two branches: re-state the pin as `const N8_SPAWN` byte-identical, or rule the
lane out of the file. **The first branch was already `A5`'s wording.** The literal `17 + 7` sat only
in `## Dependencies`, in the table and in the DoR. Taking the first branch would have fixed prose
and left the conditional in place.

**I read `src/cli.test.ts:1750-1846` and found the conditional cannot be met at all:**
- `spawned` increments inside `childOf` (`:332`, `:340`). Children are spawned at module scope, and
  `Object.keys(CHILDREN)` must equal `N8_SPAWN` (`:1834`).
- The file must import only `spawnSync` from `node:child_process`, with exactly one call site
  (`:1840-1845`).

A deep child in that file has three possible forms, and each one defeats `A5`:
1. Through `childOf`, gated at module scope: `spawned` is 28 with the variable set, so the pin is red.
2. Through `childOf`, spawned lazily inside a deep `it`: green only because the pin runs earlier in
   file order. That is an order-dependent test.
3. Through a second `spawnSync`: the pin's own source check is red.

**The cut's "conditional hand-off" was therefore a stop that would always fire.** Ruling the
placement now removes it.

- **The cost.** Construction trap 2 now binds: the new file needs one real default-lane test. That
  adds one tracked test file to the lane. It was measured at the cut as +0.09 s wall / +0.06 s CPU
  for this shape, and `A2` re-measures it.
- **Is this BA/PM's call?** Yes. It is a fence (which files may change), not a design. The Engineer
  named it as an option, and the pin's own contract forces it.

### P3 / proposal 3 — `A3`(ii): option (a) TAKEN. (b) and (c) REFUSED.

- **(a) Bound at `NFR-004` clause B's 5 s (`HARD_CEILING_MS`, `src/engine.ts:129`). Taken.**
  - The bound is measured as the child's whole wall, spawn to exit. That is the instrument `A1`
    already uses, and it is an upper bound on the reply.
  - **My three runs at `2287959`:** `node src/cli.ts --colour black --ascii </dev/null` gave real
    3.14 / 3.16 / 3.21 s, user 3.32 / 2.69 / 2.88 s, sys 0.08–0.11 s. All exited 0, at load1 13–14
    (1-min avg; 5-min ~20). That leaves ~1.8 s of headroom.
  - **Why it holds off this machine.** The search deadline is wall-clock (`src/engine.ts:464`), so a
    slower machine does not lengthen the search. Only abort granularity and startup grow with
    slowness. The granularity was 31 ms worst case on M3, and a 105 ms stall was observed. A machine
    that blows 1.8 s of headroom is breaking `NFR-004` for real, which is a true red, not a flake.
  - **No catalog or ADR change is needed.** The bound is used, not claimed. `AR-NFR004-A`'s ~3 ms
    residual over 5 s applies only above a 5 s budget, and the CLI passes 3 000.
- **(b) 3 s + 31 ms. Refused.**
  - The 31 ms is one machine's benchmark-position worst case. `AR-NFR004-A`'s own scope says a
    materially worse reading is "a NEW question".
  - The whole-child wall already reads 3.14–3.21 s, so (b) on the child instrument is red today.
  - It fails the page's own machine-independence rule.
- **(c) Drop (ii). Refused.** It would leave `A3` with no upper bound on the composed product, and
  the harness `timeout` is a hang guard, not a criterion. Dropping it would cut acceptance text,
  which this re-cut was told not to do.
- **Limit disclosed on the page (`## Risks`).** A 3–5 s budget regression passes (ii). That is
  accepted: the tight bound is `AR-NFR004-A`'s ground, and `ENGINE_DEEP` covers it in-process.
