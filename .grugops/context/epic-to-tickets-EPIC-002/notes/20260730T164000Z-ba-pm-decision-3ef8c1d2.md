`plans/tickets/` and gated against `agent-factory/checklists/definition-of-ready.md`.

**23 points. Largest is `L`. NO `SPLIT_REQUIRED`.** Epic size corrected `M` → `XL` in-file with the
reason, exactly as `EPIC-001` recorded its own `L` → `XL`; the no-XL rule binds tickets, not epics.

**What was deliberately kept apart to hold that line**, because the boundaries are the decision and
not a consequence of it:

- **`ABC-014` + `ABC-016` + `ABC-017` are three tickets, not one renderer.** Merged they are 8
  points — an `XL` and an automatic `SPLIT_REQUIRED`. They are also three genuinely different
  subjects: a board scan, six status items with four separate correctness traps, and a bounded
  two-column layout.
- **`ABC-018` is not folded into `ABC-019`.** The loop is already `L`; adding output makes it `XL`.
  They are also separable in fact: `ABC-018` is provable against stub panels of fixed height,
  because the height invariant is a property of the assembler rather than of any panel's content.
- **`ABC-012` is not folded into `ABC-019`** even though the loop is its first consumer. It is the
  substrate for four epics (`ADR-0002` binds `EPIC-002`/`004`/`005`/`006`) and it has no unbuilt
  dependency, which makes it the single most pullable thing in this decomposition.

## Two scope reductions inside the tickets, both marked

- **The captured-piece list is cut** (`ABC-016`). The epic's `captured/material balance` hid two
  quantities with two different correct derivations; wave 1 named both traps (a board diff is wrong
  after any promotion; en passant does not put the captured pawn on the destination square, so it
  must be read from `move.captured`, never `undo.captured` or `board[to]`). The **balance** is the
  number a player reads at a glance and it is a clean 64-square scan. The **list** is deferred with
  both traps written down so they are not rediscovered.
- **The engine-thinking indicator is STATIC** (`ABC-016`, `ABC-019`). Wave 1's stop-list item 3:
  an updating indicator requires `EPIC-004` to yield once per iterative-deepening iteration or to
  run in a worker, and that is a requirement that must be stated **before** `EPIC-004` is designed.
  Ruling: **`EPIC-002` does not impose it.** A static indicator satisfies the epic's scope line
  literally, needs nothing from `EPIC-004`, and is fully testable against a stub that merely takes
  time. Recorded in the epic's `## Out of scope` so `EPIC-004`'s decomposition inherits a decision
  rather than an assumption.

## One behaviour ruled that the record did not contain

**Stdin EOF terminates the loop cleanly with exit code 0 and a one-line notice** (stop-list item 6,
carried on `ABC-019`). Both answers were defensible and wave 1 correctly declined to pick. The
reasoning: exiting non-zero would report a failure for a situation in which nothing is broken. The
safety that a truncated script needs lives in **the test's assertion, not the exit code** —
`EPIC-006`'s end-to-end test asserts the *checkmate result screen*, so a script that runs out early
fails on the missing screen. Undecided, this is the shape of bug that manifests as a test that
hangs in CI.

## `ABC-011` escalated `P2` → `P1`, `Backlog` → `Ready` — its own trigger fired

`ABC-011`'s escalation trigger reads: *"rises to `P1` the moment ... **(a)** the history module of
`ADR-0002` clause 2 is decomposed or implemented under `EPIC-002`, **(b)** a supplier is wired for
`gameStatus`'s `positionCounts`"*, and *"must be `Ready` **before** whichever of those lands
first"*. `ABC-012` is **(a)** and **(b)** at once. Both are now in `Ready` together; the pull order
is the Orchestrator's. Size, acceptance, reproduction and the `NFR-005` bar are all unchanged —
only sequencing moved, which is exactly what the trigger was written to encode. Not `P0`: nothing in
flight is broken and no user-facing consumer exists.

**The consequence that made the escalation non-optional** is recorded on `ABC-012` and `ABC-019`:
both must write their threefold tests around a repeated line that **never sets an en-passant
square** (the knight cycle `src/gameend.test.ts:27-58` already uses), or the test fails for a reason
that is not the code under test. That is the "encoded assumption" `ABC-011` warned about, arriving
on schedule.

## Board and WIP

- **`Ready` goes 0/8 → 3/8.** No limit approached, **no override taken, none needed.** Three is the
  honest number: `ABC-012` and `ABC-014` are the only `EPIC-002` tickets standing on merged `src/`

- **`ABC-013` → `Blocked`, the first use of that column in this project.** It meets every

  blocks *"the merge of the first line of `src/san.ts`"*; a ticket in `Ready` is pullable, and
  pulling this one produces code that cannot land. `Blocked` is visible and time-tracked against
  `blocked_escalation_days: 2`, which is where a human ruling belongs. **`ABC-016` and `ABC-017`
  inherit the wait but stay in `Backlog`** — their blocker is a ticket, not a decision, and three
  Blocked rows would make the column lie about how many human rulings are outstanding. There is
  exactly one.
- **`EPIC-002`'s own row stays in `Backlog` with a `decomposed:` annotation.** That is precisely
  what `EPIC-001` did on 2026-07-22; it left `Backlog` only on 2026-07-24 when all seven of its
  tickets were merged. An epic row is a container — it exits `Backlog` for `Done` when its tickets
  are `Done`. **The `Backlog` exit BA/PM owns and has taken today is the ticket-level one.**
- Traceability: eight rows appended, replacing `EPIC-002`'s `pending` row; `ABC-011`'s Status cell
  updated. **No `ADR-0004` row was appended** — this file's own convention is that ADR rows land
  after ratification, and a row for a proposed decision would read as settled.

## Sizing and priority calibration, stated once

Sizes use the config scale `XS=1 S=2 M=3 L=5 XL=8` and are calibrated against `EPIC-001`'s closed
tickets rather than set by feel: `ABC-006` (perft harness) and `ABC-011` (one guarded condition +
two test shapes) anchor `S`; `ABC-002`, `ABC-005`, `ABC-007` anchor `M`; `ABC-004` (special moves)
anchors `L`. Two tickets carry a **named re-sizing condition** instead of a hedge — `ABC-019` if
the stubs need more than merged `src/` provides, and `ABC-011` if its design hop takes the strict
reading.

Priorities: `P0` = the game does not run without it (`ABC-012`, `ABC-014`, `ABC-018`, `ABC-019`);
`P1` = an epic acceptance criterion depends on it but the game runs (`ABC-013`, `ABC-015`,
`ABC-016`); `P2` = in the epic's Done and the first thing to drop if it runs long (`ABC-017`).
`ABC-015` carries a **sequencing constraint** rather than an inflated priority — `RISK-005`'s
mitigation is *"built in from the start rather than retrofitted"*, so it merges with or before
`ABC-014`, never after. That is the same pattern `ABC-011` uses, and it is the honest way to say
"low priority, fixed position in the order".
