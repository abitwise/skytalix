# The mutation campaign: 62 mutants against the delivered diff, 47 killed, 15 survived

Open item 1 came in open on every prior hop and the engineer named the standard itself: five
self-written mutants is the weakest position from which to certify a criteria set, against
`ABC-018` QE's fifty-six. This is the campaign that settles it for `ABC-009`.

## Instrument, and why the repository's `src/` was never touched

The engineer mutated `src/moves.ts` **in place** and restored it. I did not. I took a **copy** of
the repository's `src/` into this session's scratchpad with `node_modules` symlinked, and every
one of the 62 mutants was applied to that copy. **`src/moves.ts` in this repository still hashes
`0e247853ab2c05887c76105ff83d8621`** — the value the engineer published — and `git diff 8f540cf --
src/moves.ts` is empty. QE's hard limit is to test behaviour, not change it; an in-place mutation
loop is one interrupted process away from leaving a mutant in the tree, and that is not a risk worth
taking for no benefit. **It happened**: a timed-out sweep of mine left a mutant in the *scratch*
copy, which the harness's own re-hash caught. Had that loop been pointed at the repository it would
have been pointed at the delivered fix.

The driver refuses to produce a false "survived". Each mutant asserts its anchor occurs **exactly
once** in the pristine source and that the mutated bytes actually differ (otherwise `HARNESS-ERROR`,
not `SURVIVED`); the file is restored and re-hashed after every mutant; `tsc --noEmit` is run per
mutant so a mutant that is merely a broken build is never scored as a legitimate survivor. One
mutant (`M27`) reported `HARNESS-ERROR` on a non-unique anchor, was re-anchored, and re-ran — it is
counted in the 62 as a killed mutant, not quietly dropped.

The full suite ran per mutant with the JSON reporter, so the failing set is **enumerated by test
name and attributed to the criterion that owns it** rather than eyeballed.

identity test (12), reading the wrong square (6), wrong `rookFrom` table values (9), wrong piece
byte (6), loop control flow (6), guard placement (3), negation/tautology (3), option-list (2),

**`A7` killed nothing in 62 mutants.** The ticket already says `A7` asserts count *equality*, not
count *correctness*, and is not the over-rejection oracle — that was measured on one build at
refinement and is now measured on 62. It is not dead weight (it is the standing purity walk that
would have caught the original defect, and `## Test notes` 2 asks for it) but it discriminates
nothing about **this** fix, and nobody should read its green as evidence.

**The four legal-castle control rows are load-bearing, and one mutant proves it alone.** `M27` —
swapping black's kingside and queenside `rookFrom` entries — is killed by **the CONTROL rows and
nothing else**, not even by perft: in every legally-reachable position with a black castling right
both black rooks are home, so the swapped table still finds a rook. Only a position where exactly
one of the two is home can see it, and only the controls carry one.

**One correction to a figure in my own working notes, recorded because it nearly became a reported

because a 211-second deep lane with a red test would have been a serious-looking false alarm.

**zero bytes changed** on every row; `A2`'s three calls read `3, 3, 3`; the `FLAG_CASTLE` count is 0

## What this note does NOT establish

- **Which survivors are defects.** Survival alone says nothing — nine of the fifteen are genuinely
  behaviour-equivalent. That separation is the companion `observation` note's job and it was settled
  by differential test, not by argument.
- **That 62 exhausts the space.** It does not. The mutants were derived from the delivered diff's
  own degrees of freedom plus the two dimensions the criteria hold constant; a systematic mutation
  operator over the whole module would generate more.
- **Any `NFR-001` figure.** I ran no benchmark and no throughput number here is mine. Security/NFR
  owns that and follows me.
