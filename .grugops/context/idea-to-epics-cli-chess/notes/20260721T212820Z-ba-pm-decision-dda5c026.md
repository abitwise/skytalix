Four product decisions, each chosen by the requester when the ambiguity was surfaced. These constrain every downstream epic and ticket.

1. **Opening theory is a bundled static book, not a runtime fetch.** The raw request said the game "could take strategies and openings from internet". That had three readings; the requester chose build-time research compiled into a static file shipped with the package. Consequence: the game works with no network, always. Runtime queries to Lichess/ChessDB explorers are a declined non-goal, not a deferred feature.

2. **Engine strength target is club level, ~1400-1700**, with weaker selectable difficulties beneath it. This is the resolution of the requester's paired constraint "not too complex, but hard enough to be challenging". 1800+ was offered and declined as pushing past the complexity bound; ~800-1200 was offered and declined as failing the challenge bound.

3. **Stack is TypeScript on Node** — matches `.grugops/factory.config.json#default_stack.language`. Chosen over Python (search too slow to reach the strength target) and Rust/Go (stronger, but more upfront build complexity than the "not too complex" constraint allows).

4. **Move input accepts SAN and coordinate notation simultaneously**, no mode switch: `e4`/`Nf3`/`O-O` and `e2e4` are both always valid. This is the resolution of "controls should be easy to use" — a player who does not know algebraic notation can still play. Arrow-key cursor navigation was offered and declined.

Decision 3 is the only one carrying a live feasibility risk: it is sound only if Node reaches the search throughput decision 2 needs. See RISK-002 and the EPIC-004 spike.
