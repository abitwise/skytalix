### G19 and G22 were the real ones

Both are the shape the design hop warned about: a relaxation that reads as an equivalent
simplification and is not one. Probed directly against the shipped tree and against each mutant:

```
                                                 SHIPPED              G19 mutant
4k3/8/8/3nP3/8/8/8/4K3 w - d6 0 1   (enemy N)     false, pure         true, CORRUPTS
   -> 4k3/8/8/3pP3/8/8/8/4K3 w - d6 0 1           the black KNIGHT on d5 comes back a black PAWN
k7/8/8/8/3pR3/8/8/4K3 b - e3 0 1    (enemy R)     false, pure         true, CORRUPTS

                                                 SHIPPED              G22 mutant
4k3/8/8/8/3pP3/4n3/8/4K3 b - e3 0 1 (own N)       false, pure         true, pure, ep component
7k/8/3N4/3pP3/8/8/8/4K3 w - d6 0 1  (own N)       false, pure          IN THE KEY
```

`zobristKey` corrupts identically to the predicate under G19: the damage is not confined to the
predicate's own call. **The oracle answers `true` on all four**, which is the ruling's own point
restated as a measurement: off-domain the oracle is unsound and the answer is *specified*, not
derived — so "the oracle agrees with the relaxed guard" is not a defence.

All four FENs round-trip byte-identically through `toFen` and neither side is in check on any of
them, so each test isolates the ep contradiction and nothing else.

### The five survivors are equivalent, PROVED rather than assumed

Each survivor was run side by side with the shipped tree in one process over 400 random boards ×
139 `epSquare` values, comparing the **answer**, the **key** and **full-state purity**:

```
L11  inputs=55600  answerDiff=0  keyDiff=0  purityDiff=0
G10  inputs=55600  answerDiff=0  keyDiff=0  purityDiff=0
G11  inputs=55600  answerDiff=0  keyDiff=0  purityDiff=0
G16  inputs=55600  answerDiff=0  keyDiff=0  purityDiff=0
G18  inputs=55600  answerDiff=0  keyDiff=0  purityDiff=0
```

**L11 is now equivalent for a NEW reason:** guard (a) catches `epSquare === NO_SQUARE` on its own,
because `board[-1]` on a `Uint8Array` is `undefined` and `undefined !== EMPTY`. **G11 — the one-line
`||` merge of both guards — is genuinely equivalent and safe**, which is worth stating precisely
because G12 and G13, two *other* one-line merges, are not.

### Disjointness, computed rather than eyeballed

```
vs the DELIVERED suite   G1 = 4   G2 = 7   G1 n G2 = 0   G0 = 13
vs the STRENGTHENED one  G1 = 8   G2 = 11  G1 n G2 = 0   G0 = 21
G1 u G2 is a subset of G0 in both cases.
G0 \ (G1 u G2) = exactly 2 tests, both of them
  "a white pawn standing ON the ep target"  (4k3/8/8/8/3p4/4P3/8/4K3 b - e3 0 1)
```

So the Engineer's correction is exactly right: that FEN is closed by **either** guard alone and
kills **neither** single-guard mutant. 4 + 7 + 2 = 13; 8 + 11 + 2 = 21. My four new FENs split
cleanly, two per guard, so disjointness is preserved rather than blurred by the strengthening.

## 3. The purity attack — 187,328 inputs OUTSIDE the delivered sweep

The delivered sweep is 5 `parseFen` boards × 133 `epSquare` values = 665. I attacked from outside it:

```
population                                        cases     impure  threw
600 random boards x 139 ep values, five shapes:
  plain / offBoardJunk / kingless / manyKings / dense
  + targeted probes B1..B11 (off-board `rank` with an
    on-board capturer, ep target on a promotion rank,
    ep target on a castling home square, extreme and
    negative counters, all 16 castling values, an
    all-black-pawn board, an all-white-pawn board,
    fully junk-filled off-board squares)            187,328       0      0
```

Covered and clean: **hand-corrupted off-board squares** (the case the Engineer explicitly named as
unverified in its claim note, item 3), **kingless positions** (`kingSquareOf` returns −1;
`isSquareAttackedBy` reads it safely and does not throw, so the position is never left mid-mutation),
multi-king positions, `epSquare` = `NaN` / `±Infinity` / `0.5` / `−0` and out-of-array indices —
**including −256 and 256, which pass `isOnBoard` because `(-256) & 0x88 === 0`**, a trap the
delivered sweep's `[-999, -16, -2, 128, 999]` list does not contain.

**The instrument is non-vacuous.** The identical hunter run against a guard-stripped control tree
finds **1,383 impurities** over the same population. 0 versus 1,383 is the result; 0 on its own
would not be.

Two mechanical facts that explain *why* nothing got through, both checked rather than argued:
guard (a) rejects every out-of-array `target` (`board[oob]` is `undefined !== EMPTY`), and
`target` off-board implies `rank` off-board (±16 does not change the 0x88 file nibble), so guard (b)
can only pass there if an off-board square holds a piece — which is the invariant `src/position.ts`
states, and even when I violated it deliberately the make/unmake pair still round-tripped.

tree and 1,383 on the control; a hunter that reads 0 on both is measuring nothing, and that is the
same class of error as the Engineer's null-control benchmark failure, reached from a different
direction.
