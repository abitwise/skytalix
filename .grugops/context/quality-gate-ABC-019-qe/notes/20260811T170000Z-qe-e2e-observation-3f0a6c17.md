# Nine survivors: EIGHT criterion gaps for BA/PM, ONE test gap for the Engineer, ZERO code defects

> **Hand-authored, and saying so is part of the note.** `scripts/context-io.ts` — the sanctioned
> writer Workflow 16 names — does not exist in this repo or in the kit, and
> `mcp__grugops__propose_note` is not among this session's tools. The recorded precedent for the same
> gap is `.grugops/queue/done/refinement-ABC-019/claim.md`. **Nothing in this hop is a `finding`**: no
> verification stamp is issuable to this role, `05-pr-quality-gate.md`'s §14 gate machinery does not
> exist in this repo, and no note here claims a stamp or self-attests one.

**All twenty-three criteria hold as written, and I did not find a single code defect.** Every survivor
below is a place where a WRONG build is green — thirteen mutants written into `src/turn-loop.ts`, run
against the delivered suites and against the full 24-file lane, and the file restored byte-identical
after every one (md5 `c92a1776…`, asserted after each restore). The evidence table is in this hop's
`artifact-ref` note.

**The classification rule I used, stated so it can be checked rather than trusted:** a survivor is a
**criterion gap** if the criteria as WORDED do not forbid the mutant — that routes to BA/PM. It is a
**test gap** if a criterion forbids it in its own words and no assertion reaches it — that routes to
the Engineer and needs no ticket text. Exactly one of the nine is the second kind.

## G-1 — CRITERION GAP (BA/PM). Nothing clears the message region, so a rejection line survives to the end of the game

**Mutant `Q3`:** delete `messages = []` (`src/turn-loop.ts:205`). Typecheck 0, **717/717 on 24 files**.

Measured on script `["zzzz", "g1f3", "g8f6"]`, message region per frame:

| build | frame 1 | frame 2 | frame 3 | frame 4 |
|---|---|---|---|---|
| delivered | — | `not a move: zzzz` | — | — |
| `Q3` | — | `not a move: zzzz` | **`not a move: zzzz`** | **`not a move: zzzz`** |

`A5` asserts only that the item **reaches** frame 2. `A6` asserts no message at all. `## Scope` says
the rejection line and the candidate list *"live in the frame's own message region"* and that there is
no second channel — **it never says they leave it.** So a build in which every subsequent frame of the
game repeats a rejection the player already fixed is green on all twenty-three.

**Owed:** one clause on `A5`/`A6` — the frame AFTER the one carrying a non-advancing outcome's items
carries none of them.

**This is not a width claim and does not touch `ADR-0010`.** The region's ROW COUNT is fixed
(`layoutMessageRegion` returns exactly `MESSAGE_ROWS` in every branch); what persists is content, and
`W` is not asserted anywhere in this note.

## G-2 — CRITERION GAP (BA/PM). The prompt-driven `game-over` outcome has NO criterion, and the whole branch is unexecuted by the suite

full lane):

  nobody looked at because `A9b` guards only the throw path.

**`A2`'s own explicit clause is unasserted with it** — *"the same holds for a prompt-driven

ever sees reads `status in-progress`.

**Owed:** one criterion and one test-note row — the loop returns the seam's `result` and `reason`

## G-3 — CRITERION GAP (BA/PM). `A9b` bounds what the CALLER sees and nothing about what the PLAYER sees

This extends the engineer's honest non-claim #2 from *"row 14 carries no frame-count assertion"* to
**row 14 constrains no output channel at all.** Both mutants typecheck-clean, both **717/717**:

- **`Q4`** — the loop hands the **mid-mutation** position to the render seam and writes that frame,

**Owed:** a fourth `A9b` clause — no frame and no sink write between the throw and the rethrow.

## G-4 — CRITERION GAP (BA/PM). `A10` guards the ENGINE seam's move; nothing guards the INPUT seam's, and the loop corrupts the board

Probe against the **delivered** build, input seam returning `{from: a1, to: a8, piece: ROOK, captured:
EMPTY, flags: FLAG_NONE, promotion: EMPTY}` at the start position — a move no generator produced:

```
outcome  = {"result":null,"reason":"engine-threw","exitCode":0}
moves.length = 1
FEN after    = Rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/1NBQKBNR b Kk - 0 1
```

A white rook has moved a1→a8 **through its own pawn**, the black rook is gone, and the castling rights
are mangled. **No criterion is violated.** `A10` names the engine seam and nothing else, and `playMove`
documents that its precondition is a generator-owned move — which the loop enforces on one seam only.

Mutant **`Q7`** — apply `A10`'s existing legality check to the input side too — is **also 41/41 green**,
so the suite cannot tell the two builds apart **in either direction**.

`## Scope` justifies the absence only by a property of the STUB: *"It returns a generator-owned `Move`,
so it cannot get `captured`, `flags` or `promotion` wrong."* That is a statement about the test double,
not about the `InputSeam` contract `EPIC-003` replaces it under — and `[D31]` has already ruled that
this loop must not assume that seam is well-behaved.

**Owed, and this one is genuinely BA/PM's to rule either way:** the answer may legitimately be
*"`EPIC-003` owns move validity and this loop does not check it"*. The ticket currently says **neither**,
while `A10`'s own rationale — *"a result screen can never present an engine bug as a chess outcome"* —
reads across without modification. **I did not pick.**
