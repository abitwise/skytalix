# A second, deliberately differently-shaped oracle — and the `EPIC-003` round-trip identity, run one epic early and entirely outside `src/`

The external implementation is the strongest evidence on this ticket, but it is one instrument. This
note is the other half: an oracle I wrote from the PGN export grammar, built to disagree with
`src/san.ts` structurally so that a shared shortcut would show up rather than cancel out.

## Three deliberate structural differences

| decision | `src/san.ts` | this oracle |
|---|---|---|
| disambiguation | two accumulated flags, `sharesFile` then `sharesRank`, read in order | **minimal-unique-qualifier SEARCH** — the shortest of `"" → file → rank → square` for which exactly ONE legal move of that piece type matches |
| capture | `move.captured !== EMPTY` | **read from the BOARD** (`board[to]` holds an enemy) OR the en-passant flag |
| castle side | `fileOf(move.to) === 6` | **the direction the king travels** (toward the h-file is kingside) |
| suffix | `isInCheck` after `makeMove` | the enemy king's square located, then `isSquareAttackedBy` directly |

The first is the important one: it encodes the qualifier's *purpose* (make the string name exactly
one move, as cheaply as possible) rather than its *procedure*. The two definitions are provably the
same — a file separates the mover exactly when no rival shares it — but nothing about the code under
test was consulted to write it.

## The round-trip identity, one epic early

`ADR-0004` clause 2b fixes the real safety net for this grammar and the ticket says plainly it cannot
run until `EPIC-003` supplies `parseSan`:

```ts
const parsed = parseSan(position, toSan(position, move, legal), legal);
// outcome === "move" && parsed.move === move   — identity, not field equality
```

**That test ran on this hop.** An independent SAN *matcher* — regex over the PGN grammar, then a
filter across `legalMoves(position)` — was written in the scratchpad and asked, for every one of the
323,694 renders: *does this string name exactly one legal move, and is it the same `Move` object?*

**Yes, every time.** Zero strings named zero moves; zero named two or more; zero named the wrong one.

Three limits, stated so this is not read as more than it is:

1. **It is NOT `parseSan` and it is not proposed as one.** It lives outside the repository, it is not
   committed, it has no reject-reason vocabulary and no `SanParseResult`. `EPIC-003`'s contract is
   untouched and `ADR-0004` was not re-opened.
2. **It shares my reading of the grammar with my renderer.** A rule I have wrong would be wrong in
   both. That is why the external oracle exists in the note beside this one — the two checks have
   different blind spots on purpose.
3. It proves unambiguity and correct resolution. **It does not prove minimality** — `Ra1b1` would
   round-trip perfectly. Minimality is the hole the mutation note reports.

## Corners the criteria do not name, checked by hand and by both oracles

Each of these was hand-derived by me from the FEN before running anything, and each agreed:

```
N3xe4     rank disambiguation + capture           (no criterion pins a qualified capture)
Ncxe4     file disambiguation + capture
Ndxc3 / N1xc3 / Nb5xc3   the WHOLE ladder with captures, three knights on one square
O-O-O#    a castle that MATES                     (A16 pins O-O+ only)
bxc8=Q#   a capture-promotion that MATES          (A15 pins a PUSH-promotion mate only)
dxe3+     en passant giving a DISCOVERED check    (the rank opens as both pawns leave it)
cxd4 / exd4              two pawns able to take the same square
cxd8=Q / exd8=Q          two pawns able to promote onto the same square by capture
dxe3, N3e4, O-O, O-O-O, exd1=Q+   BLACK to move — none of it covered by any criterion
```

All nineteen agree with `src/san.ts` and with `chess.js`. **The corners are clean; it is the
acceptance net over them that is not.**
