# QE VERDICT: **PASS**. Zero defects in the code, five gaps in the criteria — and why the second number does not block the first

`ABC-013` moves `In Review` → `In Security/NFR`. The `In Review` exit is QE/E2E's; the
`In Security/NFR` exit is Security/NFR's and was not taken.

## The two counts, kept apart

| | count | what it means |
|---|---:|---|
| **defects in `src/san.ts`** | **0** | no input was found on which the delivered build emits a string an oracle calls wrong |
| **gaps in the ACCEPTANCE CRITERIA** | **5** | five wrong builds pass all 22 criteria AND all 652 tests |

The subtask asked for these separately and the distinction carries the verdict. A criteria gap is a
statement about what the net WOULD catch tomorrow; a code defect is a statement about what ships
today. Only the second blocks.

## Why PASS and not BLOCKED_NEEDS_FIX

1. **The build is right, and it is right by an instrument nobody here owns.** 649,556 SAN strings
   matched against an external implementation with zero mismatches; 323,694 matched against a second
   oracle built to a different shape; every emitted string round-trips to exactly the right `Move`.
   That is a stronger statement about correctness than any acceptance table can make, and it is the
   statement the ticket was missing.
2. **`A7`'s rule choice — the largest named risk — is upheld**, and no longer by a grugops reading.
3. **All 22 criteria pass, the gate is green on all four mandatory steps, and the diff is still
   three added files with zero deletions.**
4. **The five gaps are all one class and that class is the mildest one available.** Over-qualified
   disambiguation produces a string that is unambiguous, parseable, resolves to the correct move, and
   is merely not minimal — `Ra1b1` where `Rab1` was owed. It is a conformance and readability defect,
   not a correctness or a legality defect. Had the survivors been UNDER-qualifying builds I would
   have blocked, because those produce a move a reader cannot name and `EPIC-003`'s parser cannot
   resolve.

**Blocking would send back a build that is provably correct so that the net around it could be
widened.** The honest move is to pass the build, report the hole loudly, and let BA/PM cut the row
that closes it before `ABC-016`/`ABC-017` consume this function.

## Why I did not close the gap myself

Writing tests is this role's job and closing this one is small — a single property over the existing
corpus asserting that no SHORTER qualifier would also be unique, or five rows over rook, bishop,
capture and black positions I have already built and verified. **I did not add it**, deliberately:
the subtask fixed the delivered `src/` diff at three new files, 628 insertions, zero deletions and
required that property to stay true, and a fourth file breaks it.

The gap is therefore **reported and not closed**, with the recipe stated so the next hop does not
re-derive it. That is a deliberate deferral, not an oversight, and it is the one place where this
hop stopped short of what the role would normally do.

## The follow-up I recommend BA/PM cut

Not raised as a blocker; raised so it is decided rather than discovered.

- **The acceptance table asserts minimality only for WHITE knights and WHITE queens.** Rooks,
  bishops, qualified captures and every black move have no minimality assertion anywhere in the
  suite. Five wrong builds live in that hole today.
- **The table has no black-to-move position at all** — all 18 FENs are white to move. `Q13` (castle
  side by absolute square) is the natural bug that hole was built for, and it dies only on the
  Engineer's injectivity property, not on any criterion.
- The cheapest complete fix is one property, not more rows: *for every legal move of every corpus
  position, no shorter qualifier than the one emitted would also name exactly one move.* It closes
  all five survivors and `Q13`/`Q14`/`Q36` at once, needs no new expected strings, and cannot be
  written wrong in the way a hand-typed row can.

## What this verdict explicitly does NOT say

- It does not certify the criteria set complete. `ABC-023`'s hop found fourteen survivors and this
  one found five; the honest prior is that a sixth exists somewhere I did not look.
- It does not re-run `A21` on other hardware — `N2`/`N3`/`N4` remain `UNKNOWN - verify` off Apple M3
  / Node v24.12.0 / darwin-arm64, and re-running them is Security/NFR's step, which is exactly why
  the ticket goes there next.
- It does not authorise a merge. Nothing was merged and nothing was deployed; a human holds both.
