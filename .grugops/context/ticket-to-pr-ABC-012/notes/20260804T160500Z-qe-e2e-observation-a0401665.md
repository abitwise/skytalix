# The mutation campaign: 21 mutants, three survivors, and the one root cause behind all three

Every number below was produced by this role on this machine during this subtask. Where a figure
reproduces the Engineer's, that is stated as a reproduction rather than as a citation.

## 1. The harness, and the two controls it carries

The runner lives in the session scratchpad, applies one textual mutation to `src/history.ts`, runs
vitest with the JSON reporter, restores the file, and **md5-verifies the restore before the next
mutant**. Failing test titles are read off the reporter, never eyeballed. `src/history.ts` is
`12f8c562d46286e68383f8e2cab407fa` before the first cycle and after the twenty-first.

**Two controls, because a mutation table with neither proves nothing.**

- **Positive control:** the Engineer's seven mutants, re-applied. All seven die, with kill counts
  matching its published table exactly (2 / 5 / 2 / 1 / 6 / 6 / 1). The harness kills what it should.
- **Null control by construction:** one deliberately **behaviour-equivalent** mutant of `newGame`.
  It **survives**, as it must. A harness in which every mutant dies is a harness that is failing to
  apply them.

A third control was needed for the "run against the whole suite" step and is recorded because it
nearly went unchecked: vitest with an empty filter argument was verified to run **221 tests / 10
files**, not zero. A filter that matched nothing would have reported zero failures vacuously, and
every "survived" verdict below would have been worthless.

## 2. The three that survived the entire delivered suite

Applied to the shipped module and run against **all 221 tests**, not just `src/history.test.ts`:

| Mutant of the shipped `src/history.ts` | Verdict | Why the delivered suite could not see it |
|---|---|---|
| `resetTo` never copies `castling` | **SURVIVED** | `makeMove` only ever clears rights (`src/apply.ts:142`, `castling &= ~…`), so a replay starting from an already-diminished position converges on the same answer — and **no acceptance test ever takes back the move that lost a right** |
| `resetTo` never copies `blackToMove` | **SURVIVED** | `makeMove` toggles it (`src/apply.ts:146`), and all three take-back tests run from **even** ply counts (40, 40, 8), where the two errors cancel exactly |
| `resetTo` never copies `epSquare` | **SURVIVED** | `makeMove` sets the ep square on **every** move (`src/apply.ts:139`), so any replay of ≥ 1 move hides a stale one; the only test that truncates to **zero** plies anchors at startpos, where it is empty either way |

**One root cause, and it is the honest summary of the delivered suite: every acceptance test anchors
at the START position and takes back only at EVEN ply counts.** That is why exactly three of
`resetTo`'s six field copies were unobserved — the other three (`board`, `halfmoveClock`,
`fullmoveNumber`) were already killed.

**The shipped module is correct on all three.** These are suite holes, not module defects.

## 5. Why the clamp's second killer is not redundant, measured rather than assumed

The delivered clamp test over-runs by `moves.length + 5`. With the clamp removed, `splice` takes a
**negative** start, which counts from the **end** — so an over-run large enough (`plies ≥ 2 ×
length`) lands back at index 0 and looks *correct*. The delivered test is far enough out to be safe;
the tightest over-run, `plies = length + 1`, leaves `length − 1` moves and is the shape that keeps a
**different game** silently. That is the case the new test uses.
