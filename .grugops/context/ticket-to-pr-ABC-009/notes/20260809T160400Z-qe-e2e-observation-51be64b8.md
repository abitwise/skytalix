# All eight of BA/PM's counts reproduced, 0 of 8 disagreeing — and the probe that returned 11 twice returns 13 here, on SIX home squares

Two things had to be re-derived before a row could be written: the eight configurations BA/PM
measured (three of whose counts nobody else had reached) and the 13-value domain the whole
termination argument rests on. **I printed the input on every row, not the verdict.** That is the
lesson the Orchestrator recorded as the lesson of this task, and it is the only reason the numbers
below are worth anything.

## 1. The eight newly-required configurations, re-measured

Every row prints the decoded byte on the square under test, the decoded byte on the other
precondition square, the parsed castling mask, the masked/blocked columns, and only then the counts.
The instrument used for the masked column — `isSquareAttackedBy`, the same predicate the production
through-check calls — was **polarity-checked before any verdict was read**:

```
g1 with a black ROOK on h1  (4k3/8/8/8/8/8/8/4K2r w K)  -> true    expected true
g1 with no black attacker   (4k3/8/8/8/8/8/8/4K3  w K)  -> false   expected false
the predicate discriminates: verdicts admissible
```

**No discrepancy arose, so none is raised, and nothing was adjusted in either direction.** This is
the second independent derivation of `14`, `17`, `19` and of the rook-square doubling — the four
values the Orchestrator recorded that it had *not* reached. The other precondition holds on all eight
(own `ROOK` on the rook's square for the king's-square rows, own `KING` on `e1`/`e8` for the rook's),
and each row carries exactly the one right its label claims.

## 2. The count collisions, confirmed on the delivered code

```
king's square (right K)   enemy BISHOP 13 · enemy KNIGHT 13 · enemy PAWN 13     three bytes, ONE count
rook's square (right K)   enemy BISHOP  5 · enemy PAWN     5 · EMPTY       5    three bytes, ONE count
                          enemy KNIGHT 4 is the only one that differs
```

So a count-only row is interchangeable with rows for two other byte values. This is why the occupant
byte is asserted on every row, and the assertion was falsified rather than trusted — companion note.

## 3. The 13-value domain, re-measured on SIX home squares

BA/PM's first probe said **11** because its single probe board already held a white king; the
Orchestrator rebuilt that probe to check it and **got the same wrong 11 for the same reason**, in the
hand-back that had just warned about it. My probe varies the king parking **per attempt** — both
kings parked at `c3`/`f6`, then white only, then black only — so no attempt ever needs two kings of
one colour, and it prints the FEN it used for the two `KING` bytes, which are the ones the trap eats.

**Third derivation of the 13, first on the black mirrors, and it agrees with BA/PM's exactly.** The
sweep ran every code point `0x00`–`0x2FF` as a placement character; the version of this probe that
ships inside the test file sweeps `A`–`z`, which is sufficient to reach the same 13 and is asserted
there as a test rather than a comment.

## What this observation does NOT establish

- **That the 13 is the count for a non-home square or under a different parser.** Measured on the six
  home squares, through `parseFen` only. Anything writing `position.board` directly is outside it.
- **Anything about mutation.** These are delivered-tree measurements; the kill/survive verdicts are in
  the companion note and were produced by a different instrument.
- **Any `NFR-001`, perft, coverage or throughput figure.** None measured by this role at any of its
  three hops.
