## Judgement 1 — the screen model implements three escapes and THROWS on everything else

**I agree with the Engineer. It is a feature. I would NOT report it as brittleness.** But I would not
record it in the terms it was offered, because those terms understate what it costs.

**Why it is right.** A screen model that IGNORES an escape it does not implement is the purest form
of the defect class this project has now recorded seven times — a check that cannot fail. It would
silently certify a writer emitting a sequence the terminal would have obeyed. The throw is what makes
the model an oracle instead of a rubber stamp, and `M9` and `M10` in the observation note prove the
model is itself pinned: mutate `eraseToEndOfLine` to erase from column 0, or to a no-op, and `A2`,
`A4` and `A6` kill it. **A model that gates the writer and is gated by the criteria is the correct
shape. Keep it.**

**The cost the Engineer's framing does not name, and I am adding it rather than disputing the ruling.**
`M5` in the observation note replaced `\x1b[K` with `\x1b[0K`. Those are **the same sequence** —
ECMA-48 defines an omitted parameter as `0`, so `CSI K` ≡ `CSI 0 K`. That mutant is behaviourally
identical on every conformant terminal, and it turns **8 tests red**, five of them by *throwing*
`screen model: unmodelled escape`.

So the accurate statement of the property is **not** "any future writer change is gated by a model
edit". It is:

> **Any change to the BYTES the writer emits is gated by a model edit — including a change that
> emits a semantically identical sequence.** The model gates the emission's spelling, not its
> meaning.

That is still the right trade. A screen model cannot parse CSI generally without becoming a terminal
emulator, and the coding rules here forbid unrequested flexibility. But the flag as carried
(`ABC-027` `## Definition of Ready` flag 3, "should not be read as a defect when the suite goes red")
invites the next reader to interpret a red suite as ceremony. **The failure mode I want on record: the
next engineer emits `\x1b[0K`, or `\x1b[1;1H` instead of `\x1b[H`, sees five throws, reads flag 3, and
concludes the model is being fussy — when the model is right and the correct action is a two-line
model edit.** The flag should say *what* is gated (bytes, not behaviour) so the red is diagnosable.
**That is a wording improvement to a carried flag, owned by BA/PM, and it is NOT blocking.**
