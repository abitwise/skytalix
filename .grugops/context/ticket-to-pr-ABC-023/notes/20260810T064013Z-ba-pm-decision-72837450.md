# Six acceptance defects, not three — and TWO of them were unsatisfiable by construction, not just stale

The pre-check named three. **Three more were named by no pre-check**, which is this board's fifth
consecutive ticket where that happened (`ABC-018` five where three were named, `ABC-009` seven where
four were named, `ABC-022` seven then five more). All six are fixed in
`plans/tickets/ABC-023-castling-precondition-net-hardening.md`.

## The three the Orchestrator named

**D1 — `A4`'s hash pin was stale. BLOCKING, and it appears in FOUR places, not one.** `A4` required
`src/moves.ts` to hash `0e247853ab2c05887c76105ff83d8621`; the file on `main` hashes
`6335b452fc21ffe2d0f902ecab930840`, re-derived at this hop with `md5 -q` rather than taken from the
Orchestrator's note. The stale value was also in the header banner, the `## Reproduction` heading and
the `## Acceptance` preamble. All four re-pinned. The old value is retained **twice**, explicitly
labelled as the cutting hop's tree, so the two hops can be compared instead of one silently
overwriting the other.

**D2 — sixteen mutant verdicts scored against a suite that no longer exists.** All sixteen re-run at
559; see the `observation` note. Every verdict reproduces. Every figure in the ticket now carries the
suite size it was measured against, and the two Reproduction tables gained an `at cut @381` column so
staleness is visible rather than invisible next time.

**D3 — `## Dependencies` stated the `ABC-022` relationship backwards.** It called `ABC-022`
independent, *"either order works"*. `ABC-022` merged first and invalidated this ticket's acceptance.
Corrected, and generalised past the single instance: **any ticket that edits `src/moves.ts` before
this one is built re-triggers the same re-measurement**, because the dependency is one-way — this
ticket adds zero production lines and cannot affect anything. Leaving "either order works" in a
merged ticket teaches the next reader a false rule; stating only the `ABC-022` case would teach a
narrower true rule that misses the next occurrence.

## The three no pre-check named

**D4 — `A4` was ALSO unsatisfiable for a second, independent reason.** It required *"no existing test
file is modified"*. `## Scope` says `src/moves.castling.hardening.test.ts` — an **existing** file —
**gains rows**. No correct implementation of the scope could satisfy the criterion as written. This
is the same *class* as the stale hash (a criterion no correct build can meet), reached by a different
route, and it sat under the same criterion the pre-check had already flagged — which is exactly how
it survived: the flag on `A4` was read as "the hash", and the rest of the sentence was not re-read.
Restated as **additions-only**: no existing test row modified or deleted in any file, and no other
test file touched at all. That is what `## Out of scope` already meant when it said `ABC-009`'s
"existing rows, counts and verdicts are not edited", and it is verifiable at line level.

**D5 — `A5` enumerated THIRTEEN behaviour-equivalent controls while requiring fifteen.** Its
Then-clause listed: colour-blind on either square (2), the king guard's `continue` → `break`/`return`
(2), both guards below the emptiness test / below the through-check test / above the right test (3),
and the enemy `KING`/`QUEEN`/`ROOK` admissions on both squares (6). That is 13. The parenthetical
then said *"`ABC-009` measured fifteen such survivors … and this ticket must not lose one."* The two
missing are **colour-blind on BOTH squares** and the **extra "rook square non-`EMPTY`" condition** —
both named in `ABC-009`'s own mutation record. **This is this board's recurring defect shape: a
criterion narrower than what it claims.** Both restored and named, and all fifteen measured (all
survive at 559). The alternative — quietly changing "fifteen" to "thirteen" — would have made the
criterion self-consistent by weakening the bar, and would have been the wrong fix.

**D6 — `A1`'s own rows carried the exact blindness `A3` exists to police.** `A1` required four rows:
an enemy/enemy pair and an own/own pair, "each in both colours to move". The **castling side was
unconstrained**, so a conforming four-row set could sit entirely on one side — and `## Reproduction`
3 is the ticket's own measured proof that a net whose rows do not vary an axis is blind to an
admission conditional on that axis. Argued from that, and then **measured**: a pair admission
additionally conditional on the side survives 559/559 exactly as the plain pair mutant does. `A1` now
requires the four rows to vary **both** axes and names the side-conditional pair mutant in its
discriminating requirement. **Zero extra rows** — four rows already have room for 2 colours × 2 sides
across the two families.

## What I did NOT do, deliberately

- **`ABC-009` is NOT reopened.** Its `A1`–`A13` verdicts stand and none was re-measured. The fifteen
  controls were run as *this* ticket's `A5` bar. Nothing found here suggests one of them was wrong;
  had it, the brief's instruction is to say so and stop, and that is what I would have done.
- **`src/` is NOT touched.** `src/moves.ts` hashes `6335b452fc21ffe2d0f902ecab930840` before and
  after. No test row and no production line was written — this ticket's premise is a zero-line
  production diff and the rows are the engineer's hop. Every mutant ran on a copy outside the
  repository with `node_modules` symlinked.
- **No other ticket edited.** `ABC-010`, `ABC-013`, `ABC-022` untouched. `ABC-013` was **read** to
  re-check this ticket's escalation trigger, which is a read, not an edit.
- **`## Scope`, `## Out of scope`, size `S` and priority `P2` all stand.** None moved, and none was
  moved silently. The row count that could have forced `S` → larger was re-derived (9 of 13 gapped,
  17 rows, unchanged) and the one thing that would make it `L` — enumerating the 169-combination
  joint pair space — was checked and not drifted into: `A1` is still four rows and a class.
- **The `198,175` `NFR-001` count was not re-derived** and `npm run perft` was not run. The ticket now
  says plainly that **neither** hop ran it, where before it said only that the cutting role had not.
