## The two judgments the Engineer handed me, decided rather than accepted

**1. Rule 1's short-circuit belongs to Security/NFR. I AGREE, and the mutation campaign is why.**

The Engineer argued this on the `ABC-020` precedent (the engineer measures, the gate pins) and
asked to be judged rather than believed. I judged it and reached the same place by a different
road: **there is nothing here for a behavioural test to grab.** I ran the reorder as a mutant —
`hasLegalEnPassant(position) && position.epSquare !== NO_SQUARE` — and it left **all 189 tests
green**, because it is behaviour-**equivalent**: the predicate's own `NO_SQUARE` early return makes
the reordered condition return exactly the same key on every input. The same is true of dropping
the `epSquare` guard entirely. What changes is only cost — a make/test/unmake on the majority path
— and cost is `NFR-005`'s sub-bar verbatim ("the no-ep-square path is not made slower at all"). A
guard that no assertion about the key can ever fail is pinned by a **spied call count**, which is
exactly the shape `src/gameend.nfr.test.ts` has and exactly what the `ABC-020` Security/NFR gate
wrote. Writing it here would put an NFR test in QE's column and duplicate the next gate's work.

**I am not handing it over empty.** Three things go with it, so the next gate starts ahead of where
I did — the mutant strings, the fact that they are behaviour-equivalent (so a key assertion is the
wrong tool), and one result the dev hop did not have: **the reorder stops being harmless the moment
someone also deletes the predicate's own now-redundant-looking `NO_SQUARE` early return.** Both
edits together leave the suite **189/189 green** and make `zobristKey` write a stray piece onto
**off-board square 15** on `4k3/8/8/8/8/8/p7/4K3 b - - 0 1`, breaking `src/position.ts`'s stated
invariant that off-board squares stay EMPTY. That is a plausible tidy-up, not a contrived mutant,
and it is invisible to every test in the repo. Details in the `observation` note.

**2. `memory-bank/30-architecture.md`'s module table. I AGREE with the Engineer, and I would not
reorder it either.** The table is ordered by conceptual layer, not by DAG level — `Hashing` sits
between Serialization and Generation because that is what it *is*, and the file says so. The
layering line two sections down now carries the correction, dated and with the rebuild recorded.
Reordering the table would be the unrequested refactor rule 9 forbids, and it would make the table

**One imprecision I would fix rather than the ordering:** the `Hashing` row still reads as a

a reshuffle. Not taken here — it is documentation, not test coverage, and I would rather name it
