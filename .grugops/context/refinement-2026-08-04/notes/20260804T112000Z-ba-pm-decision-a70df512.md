# ITEM 2 RULED: the `ABC-015` / `ABC-014` / `RISK-005` knot is untied. `ABC-015` was written wrong; the constraint binds at `ABC-018`. `ABC-014` is pullable.

Flagged twice by the Orchestrator (2026-08-02, 2026-08-03) and untied zero times, gating `ABC-014`,
a `P0`. It is untied here, and the three documents that disagreed now say the same thing.

## The contradiction, stated exactly

Four documents, three statements:

| Document | What it said |
|---|---|
| `ABC-015` `## Dependencies` | *"this ticket merges **with or before `ABC-014` reaches `Done`**, never after"* |
| `ABC-015` `## Dependencies` | *"`ABC-014` — declares the `GlyphMode` type this returns … it is why this ticket sits behind `ABC-014` in `Backlog`"* |
| `plans/board.md` Backlog row | `[ABC-015] … blocked-until: ABC-014` |
| `ABC-014` `## Dependencies` | *"`ABC-015` … must merge **with or before this ticket's first user-visible use**"* |

**In this project `Done` MEANS MERGED** — `mode=lean`, `autonomy=pr`, and `memory-bank/60-progress.md`
says so in as many words. So row 1 required `ABC-015` to merge no later than the ticket it cannot be
**written** without (rows 2 and 3). Those are jointly satisfiable only if both merge in a single act
— i.e. only if they are one ticket, which `ABC-014`'s own size rationale deliberately rejects:
*"folding all three into one renderer ticket gives an 8-point `XL` and an automatic
`SPLIT_REQUIRED`."*

That is a genuine cycle, not a wording nit, and it is why a `P0` lane stopped twice.

## The ruling

**The real constraint is: `ABC-015` merges with or before `ABC-018`, never after.**

**`ABC-015`'s clause is the one that was written wrong. `ABC-014`'s was already right.** Row 4 says
*"first user-visible use"*, and `ABC-015` mis-copied that as *"`ABC-014` reaches `Done`"*. The two
are not the same event, and the difference is the whole knot.

**Why `ABC-014` reaching `Done` is not a user-visible use of anything**, from `ABC-014`'s own scope
rather than from preference:

- it *"returns a frame as a value — an array of strings, or one string — and **writes nothing**"*;
  `ABC-018` owns writing;
- the glyph mode is *"a **parameter**, not something this module decides — `ABC-015` decides it"*.

So merging `ABC-014` alone puts no board in front of any player, and **there is structurally no
hardcoded mode in it to retrofit.** `RISK-005` is mitigated by *"the ASCII fallback being built in
from the start rather than retrofitted"*; the thing that wording forbids is a build that shows a
player a board with a baked-in glyph mode and gains selection afterwards. `ABC-014` cannot be that
build. **`ABC-018` is** — it is the ticket that *"makes the frame a display rather than a log"*, it
assembles and emits, and it is the first thing in `EPIC-002` a player can see. `ABC-019` depends on
`ABC-018`, not the reverse, so `ABC-018` is the earliest binding point and the right one.

**The resulting chain is `ABC-014` → `ABC-015` → `ABC-018`, and it is acyclic.**

## Corrected in place, in four files, so no two documents disagree

Each carries the reason and the date, per this project's practice of correcting rather than
silently overwriting:

1. **`ABC-015`** — `## Dependencies` clause rewritten to `ABC-018`, with a dated block stating what
   the old wording was, why it was a cycle, and which document was wrong; `## Size and priority
   rationale` and `## Definition of Ready` updated to match.
2. **`ABC-014`** — clause clarified to **name** `ABC-018` as "first user-visible use", with a dated
   block recording that **this ticket was not the one that was wrong** and that it never blocked on
   `ABC-015`.
3. **`ABC-018`** — gains the constraint, plus the obligation it implies: whoever builds it takes the
   glyph mode as an argument and must not default it, hardcode it, or re-derive it from the
   environment. Recorded as a **merge-order** constraint, not a build dependency — `ABC-018` can
   still be built against a stub mode, exactly as it is against stub panels.
4. **`EPIC-002`'s `RISK-005` entry** — it had propagated the wrong wording (*"it merges with or
   before `ABC-014`"*) and is corrected with the same reasoning.

`plans/board.md` and `plans/traceability.md` carry the corrected constraint on the `ABC-015`,
`ABC-018` and `ABC-014` rows.

## What did NOT change, deliberately

- **`RISK-005`'s severity and its MITIGATION STRATEGY.** Only the event the sequencing constraint
  binds to moved. **If a later reader thinks the mitigation itself needs revisiting, that is
  Security/NFR's call under the owner's 2026-08-03 delegation of risk and NFR bars to that role, and
  not BA/PM's.** I ruled the sequencing, which is scope/priority and is this role's.
- **`ABC-015`'s `blocked-until: ABC-014`** — always correct, unchanged. The build dependency on the
  `GlyphMode` type is real.
- **`ABC-015` is NOT promoted `Backlog` → `Ready`.** Untying the merge order did not remove the build
  dependency, `ABC-014` is still unbuilt, and this board's own `Ready` test is "no unbuilt
  dependency". Promoting it would put a ticket in `Ready` that cannot be started — the exact thing
  that test exists to prevent.
- **`ABC-015`'s size, priority, scope, acceptance criteria, out-of-scope and test notes.** The knot
  was a sequencing error, not a mis-sizing.
- **`ABC-016`, `ABC-017`, `ABC-019`, `ABC-021`** — none is named by this item and none was touched.

## Why this was BA/PM's to rule and not Architect/Design's

It decides **when a ticket merges relative to another ticket**, from the product-risk wording in the
epic — sequencing and priority, which the owner's standing directive of 2026-08-03 assigns to this
role by name. It required **no** ruling about module structure: `GlyphMode`'s home is already fixed
by `ABC-014`'s scope, the selection rule is already fixed by `ABC-015`'s table, and nothing here
changes either. Had it required deciding where a type lives or how the modules depend on each other,
it would have gone to Architect/Design under the same directive.

## Consequence for the pull order

**`ABC-014` is pullable now**, for the first time. The Orchestrator declined it twice rather than
walk into the contradiction; the contradiction is resolved and **`ABC-014` never blocked on
`ABC-015` in the first place** — its own clause was the correct half. It stays `P0` and stays second
in the pull order behind `ABC-012`, which is unchanged from the 2026-07-31 sequencing.
