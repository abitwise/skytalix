## Verdict: **PASS_WITH_RISKS**

**All twenty-three criteria hold as written, and I found ZERO code defects.** Thirteen mutants, six
behaviour probes and an independent coverage run did not move a single criterion off `met`. The gates
are green and untouched: 717/717 on 24 files, lint 0, typecheck 0, skips 0, 0 behind `main`, `src/`
byte-identical.

**The risks are nine survivors, and eight of them are gaps in the CRITERIA rather than in the build.**
That split is what makes this `PASS_WITH_RISKS` and not `PASS`: the delivered loop is correct on every
one of them, and a *future* correct-looking build is not, because nothing would catch it. Two are
player-visible failure modes that would ship silently — a rejection line that never leaves the screen
(G-1) and a move from the input seam that no generator produced being played onto the board (G-4).

**Severity order, if only some can be taken:** G-2 and G-4 first (an entire untested branch, and a
board-corrupting path with no criterion), then G-1 and G-3, then G-6 (a ticket-internal contradiction
that must be ruled either way before it is inherited), then G-5, G-7, G-8. G-9 is already declared in
the ticket and needs nothing.

## Decision 1 — I added NO test to the lane, and this is a choice rather than an omission

Eight of the nine survivors are **criterion gaps**. Writing assertions for them now would be QE
answering questions the ticket does not answer — most sharply on **G-4** (does this loop validate the
input seam's move, or does `EPIC-003`?) and **G-6** (does a terminal frame follow an engine-side
termination, or does `A2`'s formula stand?). **Both are genuinely open, both have a defensible answer
either way, and a test is a ruling.** `[D31]`'s precedent is exactly this: the engineer flagged the
`either seam` gap rather than building an answer, and BA/PM's ruling was neither of the two the
engineer had considered.

The ninth (**G-7**, `A11`'s terminal-frame half) needs **no** ruling and is one assertion on a fixture
already in the file — but it is a change to `src/turn-loop.test.ts`, which is the Engineer's
deliverable, and the ticket must return for the criterion work anyway.

**Stated as a choice so it can be overruled cheaply.** If the Orchestrator would rather QE land G-7's
assertion directly, it is one `expect` on `A7`'s existing mate fixture and costs no new file and no
`N8-LANE` budget.

**What I did instead:** every survivor is reproducible from this hop's `artifact-ref` note — the exact
mutation, the exact fixture, the measured before/after. Whoever owns each one starts from a run, not
from a description.

## Decision 2 — no E2E, said plainly rather than invented

`quality.ui_e2e` is `ui-or-critical-path` and **there is no runnable UI surface**: no CLI entry point,
`AGENTS.md` records `Dev / run` and `E2E` as `UNKNOWN - verify` with the reason, and both of this
loop's seams are stubs by the ticket's own design. **No E2E was written and none was faked.** The
fourteen scripted rows already drive the loop end to end through both stub seams, which is what this
ticket's `## Test notes` means by testable-end-to-end-today. **E2E becomes possible at `EPIC-006`, not
here.**

## Decision 3 — the `ADR-0010` narrowing criterion was NOT tested, and its absence is NOT reported as a gap

It is not in the ticket, it depends on `ABC-027` which is not yet cut, and a second narrow QE pass
follows `ABC-027`'s merge and the `ADR-0009` cl. 9f real-panel re-gate. **I tested the 23 that exist.**

**And I propose NO constant-frame-width criterion.** `ADR-0010` clause 7 prohibits it and clause 3 gives
the reason: `W` composes by MAX and varies by design (`W = max(board 18, status, history)`,

asserts, measures, or proposes anything about frame width.** G-1 is about message-region CONTENT
persisting across frames; the region's ROW COUNT is fixed and its width is not mentioned.
