# The five accepted risks, each with a named owner and a place — and the six things this gate could NOT settle

Every item here is a `claim` at `confidence: UNKNOWN - verify`. **No `finding` is written on this
install — there is no §14 gate to issue a `§14-gate#<id>` stamp, `context.human_admission` is `off`
so no `human:<name>` stamp is available either, and no role may self-stamp.** None of these is
load-bearing for the PASS.

**No accepted risk here is unowned.** The role's rule is that an unowned accepted risk is a finding
nobody fixes, so each carries a named owner AND a place — an epic or a ticket — that it is booked
against.

---

## ACCEPTED RISK 1 — `takeBack(history, NaN)` silently discards the entire game

**Severity MEDIUM. Does NOT block against `security.block_on: high`. Owner: BA/PM to rule the guard;
place: `ABC-019` (the turn loop), which is the first consumer.**

QE named this and did not pin it, which was right. This gate **reproduced it on the shipped module
and extended the table well past QE's**, because the extension changes what `ABC-019` has to defend
against. From a 10-ply game:

| call | result |
|---|---|
| `takeBack(h, NaN)` | **entire game gone** — `moves.length` 10 → 0, back at the anchor, no throw |
| `takeBack(h, undefined)` | **entire game gone** |
| **`takeBack(h, "abc")`** | **ENTIRE GAME GONE — a raw string, and QE's table did not have this case** |
| **`takeBack(h, {})`** | **entire game gone** |
| `takeBack(h, null)` | no-op (coerces to 0) — safe |
| `takeBack(h, [])` | no-op (coerces to 0) — safe |
| `takeBack(h, "2")` | takes back **2** — correct by coercion |
| `takeBack(h, [3])` | takes back **3** — correct by coercion, and unintended |
| `takeBack(h, 1.5)` | takes back **2** — more than asked |
| `takeBack(h, 0.5)` | takes back **1** — more than asked |
| `takeBack(h, -1)` / `-Infinity` | no-op — correct, exactly as Decision 3 says |
| `takeBack(h, Infinity)` / `1e21` | clamps to 0 — correct, the clamp working as designed |

`Math.max(0, NaN)` is `NaN`, and `splice(NaN)` starts at index 0 — so the clamp that exists to
prevent silent corruption passes this input straight through into total silent data loss.

**The string case is the one that matters and it is new here.** `ABC-019` will parse a ply count from
user input. Both plausible implementations reach the defect: `Number.parseInt("abc")` is `NaN`, and
handing the raw token through is worse — `"abc"` destroys the game just as thoroughly, with no
`NaN` anywhere for a reviewer to notice.

**Why this is not the impossible scenario `AGENTS.md` rule 8 excludes**, agreeing with QE: a negative
`plies` is a benign no-op and rule 8 correctly excludes guarding it; `NaN` destroys the game. `NaN`
is a `number` to TypeScript, so the type system does not exclude it. The ticket's own justification
for the clamp — *"a silent-corruption path, not an impossible one"* — describes this input better
than it describes the one it was written for.

**Why it does not block:** see the ASVS ruling in this gate's observation note §4. `src/history.ts`
has **zero production importers** and `takeBack` has **no caller anywhere outside the test file**, so
there is no untrusted input and no trust boundary today. ASVS **V2.2.1 is not engaged, not failed.**
**The counterfactual is stated rather than banked: the moment `ABC-019` wires user input to this
function, V2.2.1 IS engaged, its default severity is HIGH, and it blocks.**

**Not fixed and deliberately NOT pinned by a test**, for QE's reason, which this gate agrees with: a
test asserting today's output would enshrine the behaviour and make the eventual fix look like a
regression. This gate adds no production logic.

## ACCEPTED RISK 2 — `playMove` validates nothing, and a foreign move yields a confident WRONG verdict

**Severity MEDIUM. Does NOT block. Owner: Architect/Design (SEAM 1 priced and made this call);
place: `ABC-019` / `EPIC-003`, the first parser to hand it a move.**

SEAM 1 priced a defensive `legalMoves` check at ~2–5 µs and left it out to match the core's style.
Not re-opened here. What this gate adds is the measured consequence, which is worse than the phrase
"a corrupt board" that both prior notes use: feeding a start-position move to a history anchored at
`8/8/8/8/8/8/8/K6k w - - 0 1` is accepted without error, materialises a knight, and then
`gameStatusOf` returns `{"result":"draw","reason":"insufficient-material"}` — a **well-typed,
confident, wrong terminal verdict.** ASVS **V2.3.1 PARTIAL**, for the same not-yet-engaged reason as
risk 1.

## ACCEPTED RISK 3 — `src/fen.ts` accepts out-of-range move counters

**Severity LOW. Does NOT block. Owner: BA/PM to cut it or fold it into the existing `ABC-009` /
`ABC-010` invalid-FEN family; place: `EPIC-001`'s rules core (`ABC-001`'s merged code).**

`parseFen` accepts `999999999999999999999` as a halfmove/fullmove counter. The resulting number is
not a safe integer, `toFen` round-trips it as `"1e+21"` so **FEN round-trip byte-identity breaks**,
and `gameStatusOf` on such a history reports `{"result":"draw","reason":"seventy-five-move"}` — the
game is over before it starts. Negative, non-numeric, exponential and hex counters are all correctly
rejected, so this is a **range** gap in a control that exists, not a missing control.

**It is `ABC-001`'s merged, `Done` code and out of this ticket's scope** (`AGENTS.md` rules 9 and 12
— flag, do not fix). It is recorded here rather than elsewhere because **this ticket is what makes it
reachable through a new door**: `newGame(initialFen)` is a new consumer of that boundary, and tracing
where a change touches data it did not touch before is exactly where new exposure hides. Today no
caller passes an attacker-controlled FEN.

# Six things this gate could NOT settle

## 1. Why this gate's `playMove` figure is 1.5x the Engineer's

8.2–8.6 ns here against 12.4–12.7 ns there. Both are more than 7x under the 100 ns bar so it does not
move the verdict, but this gate cannot attribute the difference: the Engineer's harness shape is not
recorded in enough detail to reproduce, and this one times bounded 2000-call batches with the rewind
outside the clock. **"We do not know why these differ" is the honest sentence.**

## 2. Whether the two `takeBack` framings resolve each other

The restore-outside-the-clock variant reads **higher** (2.92–2.93 µs) than the upper-bound variant
(2.45–2.46 µs), because it pays cold-object cost per iteration. The restore's arithmetic contribution
is ~0.017 µs, **below this instrument's resolution**. So the bound is confirmed as a bound and is
tight to within less than the instrument can see — **no claim is made that either framing resolves the
other**, and the bar is met at 0.49x and 0.59x either way.

## 3. The worst case for `gameStatusOf` across all positions

Two anchors were measured (startpos-line and kiwipete-line) and the expensive-`legalMoves` anchor
turned out **cheaper overall**, because the derive dominates and that line's replay is cheaper. The
~49.0 µs worst-case combination in the observation note is **arithmetic over the observed extremes,
not a measurement**, and no exhaustive position search was done.

## 4. Whether `EPIC-006` will ever let a user type a FEN

The ASVS ruling in §4 of the observation note turns on `initialFen` not being user-supplied. That is
true today and the ticket says `EPIC-006` owns startup and supplies it. **If `EPIC-006` ships a "load
position" command, `initialFen` becomes a user-supplied string, and risk 3 stops being LOW.** This
gate cannot settle a scope question that belongs to an epic that has not been decomposed. Named for
`EPIC-006`'s gate.

## 5. Three of QE's added tests are single-killer, and this gate did not widen them

QE recorded this against its own work by the same standard it applied to the Engineer. This gate
**agrees and declines to widen them**: they are test-suite depth, not risk, and adding assertions to
close a thinness QE already named would be gold-plating a suite that already kills 20 of 20
non-equivalent mutants. Owner: `EPIC-004`, as QE proposed.

## 6. The double-push repetition test — this gate agrees with QE's DECLINE and adds nothing

The Orchestrator named it for QE; QE declined it with a routing reason (it would assert a
`src/zobrist.ts` property, not a `src/history.ts` one, because `history.ts` only consumes
`zobristKey` and cannot distinguish two hashes). **This gate has no evidence that changes that
routing** and does not re-open it. Owner: `ABC-011`'s trace row, exactly as QE filed it.
