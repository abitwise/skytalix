# The soft half: what I believe but did not prove, and the two instrument failures at this hop

Recorded as a `claim` at `confidence: UNKNOWN - verify` because none of it is verified. **No `finding`
is admissible on this task** — there is no §14 gate in this install to issue a `§14-gate#<id>` stamp,
and `context.human_admission` is `off`, so no `human:<name>` stamp exists either. Nothing here is
self-stamped and nothing below is load-bearing.

## Instrument failures at this hop — two, both caught, both by printing the input

1. **The byte-domain probe returned 11 instead of 13.** Its single probe board already held a white
   king, so `K` on `e1` raised *"exactly one white king, found 2"* and `k` the black equivalent. Two
   KING bytes were reported absent from the *domain* when what was absent was a legal *probe board*.
   Caught because the probe prints the witness per value and two values had none. **Had I written the
   criterion on that reading, `A13` would have quantified over 11 values and dropped both KING bytes —
   one of which is the required value on the king's square.**
2. **The accounting probe drifted off the criterion's precondition.** It reported the mover's own `KING`
   on the rook's home square as *"constructible"* via `4k3/8/8/8/8/8/8/7K w K - 0 1` — a FEN that puts
   the king **on h1 with e1 empty**, which is `A4`'s shape, not the excluded one. Caught only because
   the probe prints the FEN it used. The real configuration is refused on all four constructions.

Both are the same failure this ticket has now recorded four times in different clothes: **an instrument
answered a question adjacent to the one asked, and its output was plausible.** The defence that worked
both times was cheap — print the input, not just the verdict.

## Claims I believe and did not prove

- **That `A13` is the last criterion this dimension will need.** I believe it, and the argument is
  written out to be checked rather than trusted. What makes it *believable* rather than *proven* is that
  it rests on `parseFen` being the only route into a board byte for anything expressible as a `Given`
  clause. I read `src/fen.ts:90` as the only board write in `parsePlacement` and measured the produced
  domain, but I did not audit every writer of `Position.board` across the codebase.
- **That eight rows is the right size for the newly-required region.** Eight follows `A11`'s doubling
  mechanically. A reviewer could reasonably argue four (one configuration per type per square) or
  sixteen (both colours of *occupant* per row). `A11`'s own estimate moved from *"roughly nine"* to
  fourteen when QE actually wrote it, so treat eight as an estimate, not a target.
- **That the equivalence set will still survive after the new rows land.** Two instruments agree it is
  equivalent *today*. Nobody has run it against rows that do not yet exist. The Orchestrator asked QE
  to re-confirm; I did not.
- **That a pair-conditional mutant is not worth chasing.** I argued the joint space adds nothing for the
  delivered code because the two guards are independent byte compares. That argument is about the
  delivered code only. Whether some conditional mutant survives the net after QE's rows land is
  unmeasured by anyone, and it is the kind of thing the follow-up hardening ticket exists for.
- **That the stale *"twelve criteria"* phrases in `## Implementation`, `## QE` and `## Security / NFR`
  are better left alone than corrected.** A judgement, not a measurement. The competing view — that a
  reader meeting *"survives all twelve criteria"* after `A13` exists is being misled — is reasonable,
  and if a later role decides those sections should carry a dated pointer, I would not argue against it.
