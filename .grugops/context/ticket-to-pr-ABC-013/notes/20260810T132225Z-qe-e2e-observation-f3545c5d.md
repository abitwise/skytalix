# The acceptance table holds **68** expected strings, not 52 — a number that travelled through the ticket, four notes, the board and the trace, and is re-derivable from nothing

Counted mechanically out of the delivered `src/san.test.ts`, then re-counted by hand from the
ticket's `## Acceptance` § criteria. Both give the same answer.

```
table rows (expectRows entries)            48
A1's exhaustive start-position set         20
                                        -----
expected strings asserted                  68
distinct expected strings                  63
distinct (position, move) rows             66
```

By criterion, from the ticket text: `A1` 20 · `A2` 5 · `A3` 4 · `A4` 4 · `A5` 2 · `A6` 3 · `A7` 1 ·
`A8` 4 · `A9` 2 · `A10` 2 · `A11` 2 · `A12` 8 · `A13` 1 · `A14` 1 · `A15` 4 · `A16` 3 · `A17` 2 =
**68**. Five strings repeat across criteria (`Bd2`, `Qd2`, `Nf3`, `Nbc3`, `Ndc3`), which is where 63
distinct comes from.

**No reading of the table gives 52**, and BA/PM's companion figure of *"49 distinct expected
strings"* does not match 63 either. The pair (52 rows / 49 distinct) describes **BA/PM's out-of-tree
harness table** — the one stamped `md5 56d56506…` — not the acceptance section that shipped. The
number then travelled verbatim into the ticket's own prose, into four context notes, into the board
header, into the traceability row and into this hop's subtask brief.

## Why this is worth a note rather than a silent correction

It is exactly the failure mode BA/PM itself named and repaired one hop earlier, on this same ticket:

> *(First written as "seventeen" and corrected on recount within the same hop: the enumerated list is
> the authority and it has eighteen entries … Recorded rather than quietly amended, because **a count
> nobody can re-derive from the list under it** is the same defect this hop spent its day
> repairing.)*

The same sentence applies here. **No code rides on it** — every one of the 68 is asserted, all 68
appear in the ticket (checked mechanically), and the transcription from ticket to test file is
exact. The defect is that a reader who counts the table cannot reproduce the number the table is
described by, and five documents now repeat it.

**I did not edit the ticket's prose to fix it.** Correcting BA/PM's count inside the acceptance
section is adjacent-document editing at a hop that owns the `In Review` exit and not the criteria,
and the honest record is more useful than a quiet substitution. It is one line for whoever next
touches `## Acceptance`, and the number to write is **68 expected strings (63 distinct) over 18
FENs**.
