# The 52 expected strings match the SAN standard — asserted by hand from the notation's rules, checked against no external implementation

**Claim:** every expected string in `ABC-013`'s repaired acceptance table is the SAN a chess player
and the PGN export standard would write.

**How far it is verified.** Each string was derived by hand from its FEN against the disambiguation
precedence the ticket's own `## Scope` states — no qualifier if the piece is unique, else the origin
file, else the origin rank, else the full origin square — and against the ordinary rules for pawn
captures (origin file), promotions (`=P` after the destination), and the `+`/`#` suffixes. An
independently written reference implementation, authored **after** the table was stamped, agrees on
all 52. Every position's legality and every move's existence were checked against merged `src/`.

**How far it is NOT verified.** Nothing in this repository or this session was checked against an
external SAN implementation, a PGN corpus, or the FIDE/PGN specification text. There is no such
oracle here — that is precisely why the ticket's Test notes call this table the module's only oracle
until `EPIC-003` supplies the round trip.

## The three rows I would look at first if one of them is wrong

- **`Q1e1` (from `h1`) and `Qee1` (from `e4`) on `P-QUEENS`.** These are the two middle rungs and the
  ones a careless reading gets wrong. The reasoning, stated so it can be attacked: candidates are
  `{h4, h1, e4}`; for `h1` the file `h` is shared with `h4` so the file cannot serve, while rank `1`
  is unique among the three, giving `Q1e1`; for `e4` the file `e` is unique, giving `Qee1`; for `h4`
  neither axis alone separates it, giving `Qh4e1`. This is the textbook three-queen configuration
  and I am confident in it — but it is the row where a disagreement is most likely, and the pre-check
  flagged this exact corner ("file-disambiguation is ambiguous but rank is not") as unverified.
- **`Ne4` on `P-PIN`.** Correct only if disambiguation ignores pinned rivals. The ticket's `## Scope`
  says "the other **legal** moves", and `legalMoves` on that position returns exactly one mover to
  `e4` (measured: 16 pseudo-legal, 10 legal). If any consumer ever wants pseudo-legal
  disambiguation, this row is the one that would have to change — and it should change in `## Scope`
  first.
- **`exd6` on `P-EP`.** An en-passant capture written as an ordinary pawn capture, with the
  destination being the empty en-passant square. Standard, and the row a `board[move.to]`-based
  implementation gets wrong.

**If any of these is wrong, the ticket's table is wrong and the engineer will build to it.** That is
the cost of a hand-typed oracle and it is why the Test notes forbid the alternative: a generated
expectation would agree with the implementation by construction and prove nothing at all.
