### L8 was the real one, and it is the unsafe error direction

`if (legal) return true;` → `return legal;` gives up after the **first** candidate capturer. The
predicate walks `EP_CAPTURE_SIDES = [-1, 1]`, lower file first, so the discriminating shape is "the
lower-file capturer is pinned and the higher-file one is not". The delivered suite could not see it,
and neither could a deeper property walk: over an exhaustive 518,474-node walk of the perft table at
its own `fast` depths, **exactly 2 nodes have two pseudo-legal ep capturers at all**, and in
**neither** is the lower-file one illegal while a legal one exists. The shape simply is not in that
population — it has to be built.

Built and verified against the shipped tree, both round-tripping byte-identically through `toFen`
and neither side in check:

```
2r4k/8/8/2PpP3/8/8/8/2K5 w - d6 0 1    c5xd6 illegal (pinned by the c8 rook), e5xd6 LEGAL
2k5/8/8/8/2pPp3/8/8/2R4K b - d3 0 1    c4xd3 illegal (pinned by the c1 rook), e4xd3 LEGAL  (mirror)
```

Under the mutant the key **collapses** two positions FIDE calls different. That is an
**over-collapse** — a repetition declared that never happened — and it is the opposite of the error
direction this ticket's whole priority argument rests on ("a legitimate draw is missed; a false draw
is never declared"). **The shipped code is correct on both FENs.** Closed by
`describe("ABC-011 QE edge probes")` in `src/legal.test.ts` and its key-level twin in
`src/zobrist.test.ts`.

### Z5 is real but PRE-EXISTING, not introduced by ABC-011

`EP_FILE[fileOf(position.epSquare)]` → `EP_FILE[0]` survived the branch suite. I re-ran the same
mutant against the **pre-ABC-011 baseline** (`4c6ed7d`): **174/174 green there too.** So the ep
*file* has never been load-bearing in any test in this repo — the new property test does not close
it either, because it only ever compares "key with ep" against "key with ep cleared", never two
different ep files. Consequence if it ever broke: two positions differing only in ep file hash
equal, i.e. a false repetition. Closed by one test on the pair
`4k3/8/8/1pPpP3/8/8/8/4K3 w - b6 0 1` vs `… w - d6 0 1` (a legal ep capture answers each).

### The three remaining survivors are ONE gap, and it is Security/NFR's

Z1, Z4 and L11 are **behaviour-equivalent** mutants — verified, not assumed: each leaves 189/189
green and none changes any key on any input, because the predicate's internal `NO_SQUARE` return
makes the reordered condition compute exactly the same thing. What they change is **cost**, on the
majority path, which is `NFR-005`'s sub-bar verbatim. No assertion about a key can ever fail them;
the instrument is a spied call count, the shape `src/gameend.nfr.test.ts` already has.

**The one thing the dev hop did not have, and the reason this should be pinned rather than noted:**
Z1 and L11 **together** — the reorder plus deleting the guard that then looks redundant, an
ordinary tidy-up — still leave **189/189 green**, and on
`4k3/8/8/8/8/8/p7/4K3 b - - 0 1` a single `zobristKey` call then writes a white pawn onto
**off-board square 15**, breaking the invariant `src/position.ts` states in its own comment ("Off-board
squares stay EMPTY and are never read"). Latent rather than live — `zobristKey` and `toFen` both skip
off-board squares — but it is exactly the "held by nothing" shape the `ABC-020` gate closed.

## 7. AC4's property test — non-vacuous in fact, one assertion short of pinned

Instrumented the delivered walk and separated the halves:

```
             double pushes   ep-ANSWERED   ep-UNANSWERED   violations
startpos             168             0             168             0
kiwipete              50            46               4             0
position-3            14             2              12             0
position-4            11             4               7             0
position-5           218             0             218             0
position-6            96             0              96             0
TOTAL                557            52             505             0
```

So **both halves are genuinely exercised** — 52 and 505. But the delivered assertions are
`checked > 0` and `answered > 0`, and `checked` counts double pushes of **both** kinds: a walk that
found only ep-answered pushes would satisfy both while proving nothing about the collapse case,
which is the case this ticket exists to fix. One line added — `expect(checked - answered)
.toBeGreaterThan(0)` — and the sentence in the Engineer's decision note becomes true.
